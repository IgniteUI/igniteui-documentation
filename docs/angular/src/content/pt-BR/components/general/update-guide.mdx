# Guia de atualização

No [versionamento](https://github.com/IgniteUI/igniteui-angular/wiki/Ignite-UI-for-Angular-versioning) do Ignite UI for Angular, o primeiro número sempre corresponde à versão principal do Angular suportada pelo código, e o segundo é dedicado às versões principais de lançamento. Mudanças que quebram compatibilidade podem ser introduzidas entre versões principais.
Uma lista completa das alterações de cada versão do **Ignite UI for Angular** pode ser encontrada no [CHANGELOG](https://github.com/IgniteUI/igniteui-angular/blob/master/CHANGELOG.md) do produto

O pacote Ignite UI for Angular também oferece suporte à migração automática de versões por meio dos schematics `ng update`. Eles tentarão migrar todas as mudanças que quebram compatibilidade possíveis (seletores, classes e propriedades @Input/Output renomeados); no entanto, ainda podem existir alterações que não podem ser migradas. Elas geralmente estão relacionadas à lógica de aplicação em TypeScript e serão descritas [abaixo, adicionalmente](#alterações-manuais-adicionais).

Primeiro, execute o comando [**`ng update`**](https://angular.io/cli/update), que vai analisar a sua aplicação e as atualizações disponíveis para os seus pacotes.

```cmd
ng update
```

Para atualizar o pacote licenciado **Ignite UI for Angular**, execute o seguinte comando:

```cmd
ng update @infragistics/igniteui-angular
```

Para atualizar o pacote gratuito **Ignite UI for Angular**, execute o seguinte comando:

```cmd
ng update igniteui-angular
```

Ao atualizar `@infragistics/igniteui-angular` ou `igniteui-angular`, recomenda-se atualizar os pacotes `@angular/core`, `@angular/cli` e `igniteui-cli` para as versões correspondentes.
Para atualizar o pacote **Ignite UI CLI**, execute o seguinte comando:

```cmd
ng update igniteui-cli
```

Para atualizar o pacote **Angular Core**, execute o seguinte comando:

```cmd
ng update @angular/core
```

Para atualizar o pacote **Angular CLI**, use o seguinte comando:

```cmd
ng update @angular/cli
```

<DocsAside type="info">
Se o comando `ng update` falhar por causa de incompatibilidades nas dependências dos pacotes, desfaça a atualização, exclua a pasta `node_modules` e execute a atualização novamente com a flag `--force`.
</DocsAside>

## Alterações manuais adicionais

Infelizmente, nem todas as alterações podem ser atualizadas automaticamente. As alterações abaixo estão divididas em seções conforme ocorrem nas versões; por isso, se alguma atualização for necessária, comece pela sua versão atual e aplique as atualizações seguintes de baixo para cima.

Por exemplo: se você estiver atualizando da versão 6.2.4 para a 7.1.0, comece pela seção "From 6.x ..", aplique essas alterações e siga subindo:

## De 22.2.x para 22.3.x

O Ignite UI for Angular 22.3.0 usa o Ignite UI Theming 30 (`igniteui-theming`), cuja função `palette()` cria paletas com um novo gerador `fitted` por padrão. O gerador `fitted` posiciona cada tom por contraste e o emite como uma cor fixa; por isso, uma chamada `palette()` compila para cores diferentes das anteriores. As paletas predefinidas, como `$light-material-palette`, e os temas CSS pré-compilados mantêm o gerador `legacy` e não mudam. [Geração de paletas](../themes/palette-generation.mdx) explica os dois geradores.

A migração `ng update` adiciona `$generator: 'legacy'` a cada chamada da função `palette()` nos seus arquivos `.scss` e `.sass` que ainda não escolhem um gerador, para que as suas paletas mantenham suas cores:

```scss
// Before
$my-palette: palette(
  $primary: #0099ff,
  $secondary: #df1b74,
  $surface: #ffffff
);

// After
$my-palette: palette(
  $primary: #0099ff,
  $secondary: #df1b74,
  $surface: #ffffff,
  $generator: 'legacy'
);
```

A migração não altera `@include palette(...)`, o mixin que emite uma paleta como variáveis CSS. Ela não pode adicionar o argumento a uma chamada que espalha os seus argumentos, como `palette($args...)`. Ela informa cada uma dessas chamadas, com o arquivo e a linha, ao final da saída de `ng update`; por isso, adicione `generator: 'legacy'` ao mapa espalhado manualmente.

Para mover uma paleta para o gerador `fitted`, remova o argumento `$generator`. Para manter o gerador `legacy` em todas as chamadas de `palette()` sem passar o argumento, configure a biblioteca de temas antes de qualquer outra coisa a carregar:

```scss
@use "igniteui-theming" with ($shade-generator: 'legacy');
@use "igniteui-angular/theming" as *;
```

Os temas de componentes agora obtêm o fundo do papel de superfície `base`, `--ig-surface-base`, em vez de `--ig-surface-500`. Toda paleta emite os papéis de superfície: `base`, `sunken`, `raised`, `overlay` e `container`. Os tons numerados de superfície estão obsoletos: as paletas ainda os emitem com os dois geradores, e uma paleta `fitted` aponta `--ig-surface-500` para `--ig-surface-base`, mas eles serão removidos em uma versão futura. Revise manualmente o seguinte:

- Se você substituir `--ig-surface-500` em tempo de execução, por exemplo, para mudar uma seção para uma superfície escura, substitua `--ig-surface-base` em vez disso, junto com `--ig-surface-raised`, `--ig-surface-overlay` e `--ig-surface-sunken` onde você os usa. Veja [Paletas](../themes/palettes.mdx#dark-vs-light).
- Se os seus próprios estilos lerem `--ig-surface-500` ou `color($color: 'surface', $variant: 500)`, eles continuarão funcionando por enquanto. Migre-os para um papel de superfície, como `color($color: 'surface')`, que retorna `base`, antes que os tons numerados sejam removidos.
- Se você passar um mapa de paleta escrito à mão, adicione os papéis de superfície à sua entrada `surface`. Veja [Mapas de paleta personalizados](../themes/sass/palettes.mdx#mapas-de-paleta-personalizados).

## De 22.0.x para 22.1.x

O Ignite UI for Angular 22.1.0 conclui a migração para o mixin `tokens()` e move os estilos estruturais dos componentes para o bundle de cada componente. A migração `ng update` executa automaticamente as seguintes alterações de sintaxe:

- Substitui os mixins wrapper de Sass por componente que foram removidos (`avatar`, `badge`, `banner`, `card`, `dialog`, `tabs`, os mixins de grade e de pivot, e os demais wrappers que já estavam obsoletos) por `tokens()`.
- Remove as chamadas aos mixins `-typography` por componente que foram excluídos, como `badge-typography`, `dialog-typography` e `checkbox-typography`. A tipografia agora é aplicada por meio de tokens de componente. Veja [Tipografia](/themes/sass/typography#tipografia-dos-componentes) para substituições específicas de componentes.
- Remove as importações profundas de Sass dos parciais estruturais, como `igniteui-angular/lib/core/styles/components/avatar/avatar-component`, e as chamadas `component()` correspondentes. Os estilos estruturais agora são distribuídos automaticamente com o bundle do componente.
- Renomeia as importações diretas e os usos de `IgxDividerDirective` para `IgxDividerComponent`. `IgxDividerModule` não é afetado.

Revise manualmente as chamadas `tokens()` migradas. A migração não consegue determinar se um mixin wrapper representava uma substituição comum de token universal ou dependia de declarações locais do componente. Mantenha o modo global padrão gerado, a menos que os testes ou a estrutura do tema mostrem que as declarações locais são necessárias. Nesse caso específico, adicione `$mode: 'scoped'`:

```scss
// Before
.my-avatar {
  @include avatar(avatar-theme($background: red));
}

// After
.my-avatar {
  @include tokens(
    avatar-theme($background: red),
    $mode: 'scoped'
  );
}
```

Comece com o modo global padrão, inclusive ao substituir a maioria das chamadas `css-vars()`. Se o componente permanecer na saída global `theme()`, as suas declarações locais podem consumir os tokens universais, e normalmente nenhum modo escopado é necessário.

Use o modo escopado somente quando a saída padrão não fornecer as declarações locais do componente exigidas pela personalização. Casos típicos incluem:

- O wrapper removido estabelecia um tema local completo, cujo comportamento não é preservado apenas com substituições de tokens universais.
- O componente está listado na lista `$exclude` do mixin global `theme()`. Nesse caso, o tema global não emite as declarações locais consumidas pela folha de estilos estrutural do componente.
- O tema usa expressões de dimensionamento locais ao componente. O modo global omite de propósito os valores de dimensionamento que dependem de variáveis de dimensionamento locais.
- O mapa do tema contém vários seletores, como o host do componente e um seletor de ghost ou de overlay. Overlays destacados devem receber o tema a partir de um seletor que consiga corresponder ao overlay no seu outlet, geralmente em uma folha de estilos global.
- O tema local muda o design system ou a variante claro/escuro. Passe o `$schema` correspondente para a função de tema do componente, para que o modo escopado emita os metadados corretos do tema.

Não adicione o modo escopado indiscriminadamente. Mantenha o modo global padrão para as substituições comuns de `--ig-<component>-*`, seja em toda a aplicação ou restritas por um seletor. O componente deve continuar incluído na saída global `theme()`, para que as suas declarações locais possam consumir esses tokens universais:

```scss
@include tokens(
  avatar-theme(
    $schema: $dark-material-schema,
    $background: var(--ig-primary-500)
  )
);
```

O modo escopado não elimina universalmente a necessidade de `::ng-deep`. O Emulated View Encapsulation do Angular ainda pode impedir que os seletores gerados para elementos aninhados ou internos correspondam. Mantenha `::ng-deep` onde os testes mostrarem que é necessário, ou mova essa inclusão de tema para uma folha de estilos global. Para um overlay destacado, `::ng-deep` sozinho não basta; o tema precisa corresponder ou ser herdado no outlet do overlay.

Os estilos do Ignite UI agora usam a ordem de cascata `ig.reset` → `ig.base` → a camada do design system ativa (`ig.material`, `ig.bootstrap`, `ig.fluent` ou `ig.indigo`) → `ig.derived`. Se a sua aplicação carregar uma folha de estilos de reset ou de normalize, coloque-a na camada de reset de menor precedência, para que não sobrescreva os estilos dos componentes:

```scss
@layer ig.reset {
  @import "minireset.css";
}
```

Para detalhes, veja [Temas de componentes](/themes/sass/component-themes) e [Temas globais](/themes/sass/global-themes#excluindo-componentes).

## De 21.1.x para 22.0.x

O Angular não distribui mais o `HammerModule` para gestos de toque. Para manter as interações por toque (arrastar, deslizar, tocar) funcionando nos componentes do Ignite UI for Angular, carregue o HammerJS como um script global por meio do array `scripts` no seu `angular.json`:

```json
"architect": {
  "build": {
    "options": {
      "scripts": [
        "node_modules/hammerjs/hammer.min.js"
      ]
    }
  }
}
```

Depois de carregado globalmente, o Ignite UI for Angular detecta automaticamente o `window.Hammer` e o usa para tratar os gestos de toque, sem necessidade de importações adicionais ou registros de módulo.

## De 21.0.x para 21.1.x

A versão 21.1.0 traz um novo mixin `tokens` que pode ser usado no lugar do mixin `css-vars`, agora obsoleto, do nosso framework de temas em Sass. Na superfície, é uma mudança cosmética; no entanto, o novo mixin `tokens` produz tokens universais de tema global de componentes que funcionam em todos os nossos frameworks Ignite UI. O mixin `css-vars` agora está obsoleto e será removido em uma versão futura; por isso, recomendamos mudar para o novo mixin `tokens` o quanto antes.

O mixin `tokens` gera tokens de variáveis CSS para componentes nos modos `global` ou `scoped`, com uma cadeia de fallback universal `--ig-*` e a reescrita adequada das referências locais de tokens.

**Modo global** (padrão) — emite os tokens universais `--ig-{component}-{property}`. As referências locais `var()` são reescritas para os seus equivalentes globais, para que os valores derivados (por exemplo, `adaptive-contrast`) sejam resolvidos corretamente em qualquer escopo. As expressões de dimensionamento são ignoradas; informe valores concretos em vez disso.

```scss
// Input:
@include tokens(avatar-theme($background: red));

// Output:
:root {
  --ig-avatar-background: red;
  /* ... remaining avatar properties ... */
}
```

**Modo escopado** — emite variáveis com escopo de componente (`--{property}`) com uma cadeia de fallback: prefixo configurado (`--igx-*`) -> universal (`--ig-*`) -> padrão do schema. Quando chamado na raiz da folha de estilos, o `selector` do tema é usado para criar a regra. Quando chamado dentro de um seletor, tanto o seletor atual quanto o seletor do componente recebem as variáveis. Na prática, isso produz o mesmo resultado do mixin `css-vars`, agora obsoleto.

```scss
// Input (from root):
@include tokens(avatar-theme($background: red), $mode: 'scoped');

// Output:
igx-avatar {
  --background: var(--igx-avatar-background, var(--ig-avatar-background, red));
  /* ... remaining avatar properties ... */
}
```

```scss
// Input (from within a selector):
.my-theme {
  @include tokens(avatar-theme($background: red), $mode: 'scoped');
}

// Output:
.my-theme,
.my-theme igx-avatar {
  --background: var(--igx-avatar-background, var(--ig-avatar-background, red));
  /* ... */
}
```

<DocsAside type="info">
No modo escopado, a propriedade `selector` do mapa de tema produzido é necessária para determinar o seletor do componente e o escopo correto das variáveis. Se o mixin for chamado na raiz da folha de estilos, a regra gerada usará o valor interno `selector` do tema. Se for chamado dentro de um seletor, tanto esse seletor quanto o seletor do componente receberão as variáveis.
</DocsAside>

```scss
// Global override:
:root {
  @include tokens(avatar-theme($background: orange));
}
// Result: --ig-avatar-background: orange;

// Scoped consumption (no explicit override):
@include tokens(avatar-theme($schema: $schema), $mode: 'scoped');
// Result: --background resolves through var(--igx-avatar-background, var(--ig-avatar-background, #000))
//         and picks up the global orange value from --ig-avatar-background.
```

<DocsAside type="info">
**As substituições globais fluem para o modo escopado.** Como as variáveis escopadas usam os tokens `--ig-*` como fallback, definir um token global em `:root` será propagado para todas as instâncias escopadas:
</DocsAside>

## De 20.x para 21.0.x

### Suporte a múltiplos pontos de entrada

A versão 21.0.0 introduz **múltiplos pontos de entrada** para melhor tree-shaking e divisão de código. O ponto de entrada principal (`igniteui-angular`) continua totalmente compatível com versões anteriores, mas recomenda-se migrar para os pontos de entrada granulares para obter os melhores tamanhos de bundle.

**Principais mudanças:**
- Componentes organizados em pontos de entrada dedicados (por exemplo, `igniteui-angular/grids/grid`, `igniteui-angular/button`)
- Alguns componentes foram realocados (diretivas de entrada, autocomplete, radio group)
- Renomeação de tipo: `Direction` → `CarouselAnimationDirection`

**Migração:**

Ao atualizar, você será solicitado a migrar as importações automaticamente:

```cmd
ng update igniteui-angular
```

Escolha **"Yes"** quando solicitado, ou migre depois com:

```cmd
ng update igniteui-angular --migrate-only --from=20.1.0 --to=21.0.0
```

Para todos os detalhes sobre os pontos de entrada, as opções de migração, as mudanças que quebram compatibilidade e exemplos de uso, veja o [guia Code Splitting and Multiple Entry Points](/general/code-splitting-and-multiple-entry-points).

### Refatoração da injeção de dependência

Toda a injeção de dependência interna agora usa a API `inject()`. Isso geralmente não afeta o código da aplicação, mas, se você estender componentes ou serviços do Ignite UI, pode ser necessário atualizar os seus construtores para usar `inject()` em vez de parâmetros de construtor.

## De 17.0.x para 17.1.x

### Geral

- `IgxGrid`, `IgxTreeGrid`, `IgxHierarchicalGrid`
  - **Mudanças que quebram compatibilidade**
    - Os eventos `rowAdd` e `rowDelete` agora emitem um argumento de evento do tipo `IRowDataCancelableEventArgs`, em vez de `IGridEditEventArgs`. As duas interfaces ainda são compatíveis, mas, para esses eventos, as propriedades redundantes `cellID`, `newValue`, `oldValue`, `isAddRow` estão obsoletas em `IRowDataCancelableEventArgs` e serão removidas em uma versão futura. Mudar para as novas interfaces corretas deve revelar qualquer uso obsoleto que possa ser removido com segurança.
  - **Obsolescências**
    - A propriedade `rowID` está obsoleta nas seguintes interfaces: `IGridEditDoneEventArgs`, `IPathSegment`, `IRowToggleEventArgs`, `IPinRowEventArgs`, `IgxAddRowParent` e será removida em uma versão futura. Use `rowKey` em vez disso.
    - A propriedade `primaryKey` está obsoleta nas seguintes interfaces: `IRowDataEventArgs`, `IGridEditDoneEventArgs`. Use `rowKey` em vez disso.
    - A propriedade `data` está obsoleta na seguinte interface: `IRowDataEventArgs`. Use `rowData` em vez disso.

### Mudanças que quebram compatibilidade

- Na versão 17.1.x, o tipo `icon` da diretiva `igxButton` foi alterado para a diretiva `igxIconButton` do tipo `flat`. Migrações automáticas estão disponíveis e serão aplicadas em `ng update`. No entanto, algumas das propriedades de entrada de `igxButton` que podiam ser usadas com botões do tipo `icon` não podem ser aplicadas aos novos `igxIconButton` criados. Se você usou as propriedades `igxButtonColor` ou `igxButtonBackground` com um botão do tipo `icon`, atualize-o da seguinte forma:

```html
// version 17.0.x
<button igxButton="icon" [igxButtonBackground]="'red'">
    <igx-icon fontSet="material">search</igx-icon>
</button>

// version 17.1.x
<button igxIconButton="flat" [style.background]="'red'">
    <igx-icon fontSet="material">search</igx-icon>
</button>
```

**OBSERVAÇÃO**: os usuários precisam adicionar manualmente `IgxIconButtonDirective` às suas importações:

```typescript
import { IgxIconButtonDirective } from 'igniteui-angular';

@Component({
    ...
    imports: [IgxIconButtonDirective]
})
```

## De 16.1.x para 17.0.x

### Geral

- Na versão 17.0, o Angular removeu os pacotes `@nguniversal/*`. Se o projeto usar esses pacotes, uma chamada padrão de `ng update` causará um erro nas migrações `igniteui-angular`, por causa de `package-lock.json` modificado de forma inadequada; mais detalhes podem ser encontrados em [issue #13668](https://github.com/IgniteUI/igniteui-angular/issues/13668). Para atualizar para `17.0.x`, é preciso seguir uma das etapas adicionais a seguir:
  - Exclua o arquivo `package-lock.json` antes de executar `ng update`
  - Execute `npm dedupe --legacy-peer-deps` antes de executar `ng update igniteui-angular`

**Mudança que quebra compatibilidade**

- Nos argumentos do evento `selectionChanging` de `IgxCombo`, o tipo `IComboSelectionChangingEventArgs` tem estas mudanças:
  - As propriedades `newSelection` e `oldSelection` foram renomeadas para `newValue` e `oldValue`, respectivamente, para refletir melhor a sua função. Assim como `value` do Combo, elas emitirão os valores de propriedade especificados ou os itens de dados completos, dependendo de `valueKey` estar definido ou não. Migrações automáticas estão disponíveis e serão aplicadas em `ng update`.
  - Duas novas propriedades, `newSelection` e `oldSelection`, são expostas no lugar das antigas, que não são mais afetadas por `valueKey` e emitem consistentemente itens de `data` do Combo.
  - As propriedades `added` e `removed` agora sempre contêm itens de dados, independentemente de `valueKey` estar definido. Isso as alinha às propriedades atualizadas `newSelection` e `oldSelection`.

Se o seu código no manipulador do evento `selectionChanging` dependia de ler `valueKeys` a partir do argumento do evento, atualize-o da seguinte forma:

```typescript
  // version 16.1.x
  public handleSelectionChanging(e: IComboSelectionChangingEventArgs): void {
    this.addedItems = e.added;
    this.removedItems = e.removed;
  }

  // version 17.0.x
  public handleSelectionChanging(e: IComboSelectionChangingEventArgs): void {
    this.addedItems = e.added.map(i => {
       return i[e.owner?.valueKey]
    });
    this.removedItems = e.removed.map(i => {
       return i[e.owner?.valueKey]
    });
  }
```

- `getCurrentResourceStrings` foi removido. Use as importações específicas das strings de cada componente.
  - Por exemplo, as strings em EN vêm de `igniteui-angular`: `import { GridResourceStringsEN } from 'igniteui-angular';`
  - Por exemplo, as strings em DE ou de outros idiomas vêm de `igniteui-angular-i18n`: `import { GridResourceStringsDE } from 'igniteui-angular-i18n';`

    Exemplos de uso podem ser encontrados na documentação atualizada de [Localização (i18n)](/general/localization).

## De 16.0.x para 16.1.x

### Geral

#### **Mudanças que não quebram compatibilidade**

- Estamos deixando de usar o token de injeção `DisplayDensityToken` para definir o tamanho dos componentes, em favor de uma forma mais simples e robusta: propriedades CSS personalizadas. Por esse motivo, o token de injeção `DisplayDensityToken` agora está obsoleto. Isso afeta todos os componentes que expõem a propriedade de entrada `displayDensity`. O token e as propriedades de entrada serão removidos na versão 17.0.0. Recomendamos que você faça o seguinte:

Remova todas as declarações em que `DisplayDensityToken` é fornecido:

```typescript
// *.component.ts
// remove the provider declaration for `DisplayDensityToken`
providers: [{ provide: DisplayDensityToken, useValue: { displayDensity: DisplayDensity.compact } }],
```

Remova todas as vinculações ou atribuições programáticas à propriedade de entrada `displayDensity`:

```html
{/* Remove `[displayDensity]="'compact'"` */}
<igx-grid [displayDensity]="'compact'">...</igx-grid>
```

Em vez disso, use a propriedade CSS personalizada `--ig-size` para obter o mesmo resultado que com `displayDensity`:

```css
/* 
Add --ig-size to a component or global file.
Available values are:
  - compact: --ig-size-small
  - cosy: --ig-size-medium
  - comfortable: --ig-size-large
*/
igx-grid {
    --ig-size: var(--ig-size-small);
}
```

## De 15.1.x para 16.0.x

- A atualização para o Angular 16 traz mudanças na forma como `NgModules` funcionam por trás dos panos. Antes, adicionar um módulo que dependia internamente de outro fazia com que as declarações de ambos ficassem disponíveis na sua aplicação. Esse comportamento não era intencional, e o Angular 16 o altera. Se a sua aplicação dependia desse comportamento, por exemplo, se você importava apenas um módulo que contém muitas dependências internas, como `IgxGridModule`, e usava componentes vindos delas, será preciso adicionar manualmente os módulos de cada componente que a sua aplicação usa, separadamente.

- **Mudanças que quebram compatibilidade**

```scss
// _variables.scss
// free version
@import '~igniteui-angular/lib/core/styles/themes/index';
```

```scss
@use '@infragistics/igniteui-angular/theming' as *;
```

- Paletas e esquemas:

- As variáveis CSS de paleta não se referem mais a valores HEX; em vez disso, representam uma lista de 3 valores H, S e L, o que significa que devem ser passadas para as funções CSS `hsl` ou `hsla`.

Antes:

```scss
.some-class {
    background: var(--igx-surface-500); // returns HEX color
}
```

Depois:

```scss
.some-class {
    background: hsl(var(--igx-surface-500)); // returns a list of H, S, L
}
```

Isso foi feito para que as paletas possam ser alteradas em tempo de execução usando apenas variáveis CSS. Assim, o canal alfa de uma cor de paleta pode ser modificado em tempo de execução sem afetar a cor base da paleta.

- Certifique-se de passar a paleta e o schema de componente corretos para os seus temas globais e de componentes personalizados. Se você quiser criar um tema escuro global, escolha um tom mais claro para a sua cor cinza, por exemplo:

```scss
$my-dark-palette: palette(
    $primary: olive,
    $secondary: yellow,
    $grays: #fff
);

@include dark-theme($palette: $my-dark-palette);
```

Da mesma forma, os temas claros exigem um tom de cinza mais escuro e um schema de cores claro.

Se você não excluiu nenhum tema de componente do tema global, mas ainda quer criar os seus próprios temas de substituição usando o mixin `css-vars`, certifique-se de que o tema receba a paleta correta e o schema correspondente:

```scss
$my-custom-grid: grid-theme(
    $palette: $my-dark-palette,
    $schema: $dark-schema
);

@include css-vars($my-custom-grid);
```

- Temas de componentes excluídos:

Caso você tenha excluído alguns temas de componentes do tema global e criado temas de substituição personalizados, certifique-se de que o mixin do componente esteja incluído e de que receba o tema de componente correto:

```scss
$my-dark-palette: palette(
    ...
    $exclude: ('igx-grid')
);

$my-custom-grid: grid-theme(
    $palette: $my-dark-palette,
    $schema: $dark-schema
);

// Ensuregrid is included:
@include grid($my-custom-grid);
```

Caso os seus temas de componentes personalizados sejam declarados em um arquivo Sass de componente separado, além do `styles.scss` global, certifique-se de que o mixin `core` também esteja incluído.

```scss
// free version
@use 'igniteui-angular/theming' as *;

// licensed version
@use '@infragistics/igniteui-angular/theming' as *;

// Include the core module mixin.
@include core();

// Create your theme.
$my-custom-grid: grid-theme(
    $palette: $my-dark-palette,
    $schema: $dark-schema
);

// Include your custom theme styles.
@include grid($my-custom-grid);
```

### Migração de IgxGridCell

- _IgxGridCellComponent_, _IgxTreeGridCellComponent_, _IgxHierarchicalGridCellComponent_, _IgxGridExpandableCellComponent_ não são mais expostos na API pública.

```ts
const cell = grid.getCellByColumn(0, 'ProductID');     // returns IgxGridCell

const cell = grid.getCellByColumnVisibleIndex(0, 0);   // returns IgxGridCell

const selectedCells = grid.selectedCells;              // returns IgxGridCell[]
const cells = grid.getColumnByName('ProductID').cells; // returns IgxGridCell[]
```

- A propriedade `cell` nos argumentos dos eventos `IGridCellEventArgs` emitidos pelos eventos _cellClick_, _selected_, _contextMenu_ e _doubleClick_ agora é uma instância de <ApiLink type="GridCell" />
- A propriedade `let-cell` no template de célula agora é `IgxGridCell`.

- _getCellByIndex_ e outros métodos vão retornar undefined se a linha naquele índice não for uma linha de dados, mas sim um IgxGroupByRow, um IgxSummaryRow, uma linha de detalhes etc.

### Temas

Devido a reclamações sobre avisos de compilação (veja [#9793](https://github.com/IgniteUI/igniteui-angular/issues/9793)), agora usamos a função [`math.div`](https://sass-lang.com/documentation/modules/math#div); essa funcionalidade é compatível com o [Dart Sass](https://sass-lang.com/dart-sass) a partir da versão 1.33.0.

#### Solução

Se, por algum motivo, você vir erros de compilação do Sass dizendo que `math.div` não é uma função conhecida, isso significa que o seu projeto usa uma versão desatualizada do Sass.

1. Atualize para a versão mais recente do Angular usando `ng update` - o Angular 12.1.0+ usa o compilador dart-sass por padrão.

    ```sh
    ng update [options]
    ```

    Se, por algum motivo, você não usa o Ignite UI/Angular CLI, será preciso substituir `node-sass` por `sass` no seu projeto Node.

    ```sh
    npm uninstall node-sass
    npm install sass --save-dev
    ```

2. Se, por algum motivo, você não conseguir atualizar para a versão mais recente do Angular pelo método acima, pode voltar ao método antigo de divisão do Sass, definindo uma flag global no seu arquivo Sass:

    ```scss
    $__legacy-libsass: true;
    ```

Recomenda-se atualizar via **ng update** para migrar as definições existentes de **igx-bottom-nav** para as novas.

- Template
  - A nova estrutura define componentes de item da navegação inferior, cada um envolvendo um componente de cabeçalho e um componente de conteúdo.             </igx-bottom-nav-content>
    ```html
        </igx-bottom-nav-item>
        ...
    </igx-bottom-nav>
    ```

- Mudanças na API
  - As propriedades `id`, `itemStyle`, `panels`, `viewTabs`, `contentTabs` e `tabs` foram removidas. Atualmente, a propriedade <ApiLink type="BottomNav" member="items" label="items" /> retorna a coleção de abas.
  - As seguintes propriedades foram alteradas:
    - A propriedade `isSelected` do item de aba foi renomeada para `selected`.
    - A propriedade `selectedTab` foi renomeada para <ApiLink type="BottomNav" member="selectedItem" label="selectedItem" />.
  - Os eventos `onTabSelected` e `onTabDeselected` foram removidos. Introduzimos três novos eventos, <ApiLink type="BottomNav" member="selectedIndexChanging" label="selectedIndexChanging" />, <ApiLink type="BottomNav" member="selectedIndexChange" label="selectedIndexChange" /> e <ApiLink type="BottomNav" member="selectedItemChange" label="selectedItemChange" />, que oferecem mais flexibilidade e controle sobre a seleção das abas. Infelizmente, ter uma migração adequada para essas mudanças de evento é, no mínimo, complicado; por isso, eventuais erros devem ser tratados no nível do projeto.

## De 8.1.x para 8.2.x

- IgxDrag
  - Como as entradas `hideBaseOnDrag` e `visible` estão sendo descontinuadas, para obter a mesma funcionalidade na sua aplicação, você pode usar qualquer forma de ocultar o elemento base que o Angular oferece. Um exemplo é definir o estilo `visibility` como `hidden`, já que isso apenas o torna invisível e mantém o espaço que ele ocupa no DOM:

    ```html
    <div igxDrag [ngStyle]="{ 'visibility': targetDragged ? 'hidden' : 'visible' }"
        (dragStart)="onDragStarted($event)" (dragEnd)="onDragEnded($event)">
        Drag me!
    
    </div>
    ```

    ```typescript
    public targetDragged = false;

    public onDragStarted(event) {
        this.targetDragged = true;
    }

    public onDragEnded(event) {
        this.targetDragged = false;
    }
    ```

  - Como `animateOnRelease` e `dropFinished()` também estão sendo descontinuadas, qualquer uso do método `dropFinished()` deve ser substituído por `transitionToOrigin()`. Caso contrário, você precisaria chamar `transitionToOrigin()`, dependendo de quando quiser que o elemento arrastado faça a transição de volta à sua localização original. Observe que, se a posição do elemento arrastado no DOM for alterada, a sua localização original também mudará com base nisso.

- IgxDrop
  - Como a estratégia de soltura padrão fornecida com a diretiva `IxgDrop` não é mais aplicada por padrão, para continuar com o mesmo comportamento, você precisa definir a nova entrada `dropStrategy` como a implementação `IgxAppendDropStrategy` fornecida.

    ```html
    <div igxDrop [dropStrategy]="appendStrategy"></div>
    ```

    ```typescript
    import { IgxAppendDropStrategy } from 'igniteui-angular';
    // import { IgxAppendDropStrategy } from '@infragistics/igniteui-angular'; for licensed package

    public appendStrategy = IgxAppendDropStrategy;
    ```

  - Qualquer uso das interfaces `IgxDropEnterEventArgs` e `IgxDropLeaveEventArgs` deve ser substituído por `IDragBaseEventArgs`.
  - Também, qualquer uso da interface `IgxDropEventArgs` deve ser substituído por `IDropDroppedEventArgs`.

- IgxRowDragDirective
  - Os nomes dos argumentos de `IRowDragStartEventArgs` e `IRowDragEndEventArgs` foram alterados para deixar mais claro a que se referem. O argumento `owner` foi renomeado para `dragDirective`.
    O argumento `owner` agora fornece uma referência ao componente proprietário. Se o seu código era assim:

    ```typescript
    public dragStart(event) {
        const directive = event.owner;
    }
    ```

    A partir da versão 8.2.x, ele deve ser atualizado para:

    ```typescript
    public dragStart(event) {
        const directive = event.dragDirective;
        const grid = event.owner;
    }
    ```

- IgxCombo
  - A forma como o [`igx-combo`](/inputs/combo/overview) trata a seleção e a vinculação de dados foi alterada.

  - Se a entrada [`valueKey`] do combo estiver definida, o controle vai procurar essa propriedade específica no array de itens de dados informado ao realizar a seleção.
**Todos** os eventos de seleção são tratados com o valor da propriedade `valueKey` dos itens de dados.
    Todos os combos que têm `valueKey` especificado devem ter a seleção/vinculação bidirecional composta apenas pelos valores da propriedade do objeto especificada na entrada:

    ```html
    <igx-combo [data]="cities" valueKey="id" displayKey="name"></igx-combo>
    ```

    ```typescript
    export class MyExampleCombo {
        public data: { name: string, id: string }[] = [{ name: 'London', id: 'UK01' }, { name: 'Sofia', id: 'BG01' }, ...];
        ...
        selectFavorites() {
            // Selection is handled with the data entries' id properties
            this.combo.selectItems(['UK01', 'BG01']);
        }
    }
    ```

  - Se o combo **não** tiver um `valueKey` definido, **todos** os eventos de seleção são tratados com **igualdade (===)**.
    Todos os combos que **não** têm um `valueKey` especificado devem ter a seleção/vinculação bidirecional tratada com **referências** aos seus itens de dados:

    ```html
    <igx-combo [data]="cities" displayKey="name"></igx-combo>
    ```

    ```typescript
    export class MyExampleCombo {
        public data: { name: string, id: string }[] = [{ name: 'London', id: 'UK01' }, { name: 'Sofia', id: 'BG01' }, ...];
        ...
        selectFavorites() {
            // Selection is handled with references to the data entries
            this.combo.selectItems([this.data[0], this.data[1]]);
        }
    }
    ```

    Você pode ler mais sobre como configurar o combo no [readme](https://github.com/IgniteUI/igniteui-angular/blob/master/projects/igniteui-angular/src/lib/combo/README.md#value-binding) e na [documentação oficial](/inputs/combo/overview#value-and-selection).

## De 8.0.x para 8.1.x

- O componente `igx-paginator` foi introduzido como um componente standalone e também é usado nos componentes de grade.
Lembre-se de que, se você definiu o `paginationTemplate`, talvez seja preciso modificar o seu CSS para exibir a paginação corretamente. Isso acontece porque o template não é mais aplicado dentro de um contêiner específico de paginação com regras de CSS para centralizar o conteúdo; por isso, talvez seja necessário adicioná-las manualmente.
O estilo deve ser algo semelhante a:

```html
<igx-grid #grid [data]="data" [paging]="true" [perPage]="10" [paginationTemplate]="pager">
</igx-grid>
<ng-template #pager>
    <div class="pagination-container"></div>
</ng-template>
```

```css
.pagination-container {
 display: flex;
 justify-content: center;
 align-items: center;
}
```

## De 7.3.x para 8.0.x

- Durante a atualização, se você encontrar o seguinte erro `Package "@angular/compiler-cli" has an incompatible peer dependency to "typescript" (requires ">=3.1.1 <3.3", would install "3.4.5").`, deve atualizar primeiro o pacote `@angular/core`. Isso está relacionado a este [problema conhecido do Angular CLI](https://github.com/angular/angular-cli/issues/13095)
- Durante a atualização do pacote `igniteui-angular`, se você vir o seguinte erro `Package "igniteui-angular" has an incompatible peer dependency to "web-animations-js" (requires "^2.3.1", would install "2.3.2-pr208")`, deve atualizar usando `ng update igniteui-angular --force`. Isso pode acontecer se você atualizar `@angular/core` e `@angular/cli` antes de atualizar `igniteui-angular`.

## De 7.2.x ou 7.3.x para 7.3.4

- Se você usar o método `filterGlobal` de `IgxGrid`, `IgxTreeGrid` ou `IgxHierarchicalGrid`, saiba que o parâmetro `condition` não é mais opcional. Quando o método `filterGlobal` é chamado com uma condição inválida, ele não limpa os filtros existentes de todas as colunas.

## De 7.1.x para 7.2.x

- Se você usar um IgxCombo com `combo.value`, saiba que agora `combo.value` é apenas um getter.
- Se você usar `IgxTextHighlightDirective`, saiba que a propriedade de entrada `page` está obsoleta. As propriedades `rowIndex`, `columnIndex` e `page` da interface `IActiveHighlightInfo` também estão obsoletas. Em vez disso, foram adicionadas as propriedades opcionais `row` e `column`.
- Se você usar `button-theme`, saiba que `$button-roundness` foi substituído, para cada tipo de botão, por: `$flat-border-radius`, `$raised-border-radius`, `$outline-border-radius`, `$fab-border-radius`, `$icon-border-radius`.

## De 7.0.x para 7.1.x

- Se você usar um IgxGrid com resumos na sua aplicação, saiba que agora o método `IgxSummaryOperand.operate()` é chamado com dados vazios para calcular a altura necessária para a linha de resumo. Para operandos de resumo personalizados, o método deve sempre retornar um array de IgxSummaryResult com o tamanho adequado.

 Antes da versão 7.1:

```typescript
export class CustomSummary extends IgxNumberSummaryOperand {
 public operate(data?: any[]): IgxSummaryResult[] {
  return [{
   key: 'average',
   label: 'average',
   summaryResult: IgxNumberSummaryOperand.average(data).toFixed(2)
  }];
 }
}
```

 Desde a versão 7.1:

```typescript
export class CustomSummary extends IgxNumberSummaryOperand {
 public operate(data?: any[]): IgxSummaryResult[] {
  return [{
   key: 'average',
   label: 'average',
   summaryResult: data.length ?  IgxNumberSummaryOperand.average(data).toFixed(2) : null
  }];
 }
}
```

# Guía de actualización

En el [versionado](https://github.com/IgniteUI/igniteui-angular/wiki/Ignite-UI-for-Angular-versioning) de Ignite UI for Angular, el primer número coincide siempre con la versión principal de Angular que admite el código, y el segundo está reservado para las versiones principales. Pueden introducirse cambios importantes entre las versiones principales.
Puede encontrar una lista completa de los cambios de cada versión de **Ignite UI for Angular** en el [CHANGELOG](https://github.com/IgniteUI/igniteui-angular/blob/master/CHANGELOG.md) del producto.

El paquete Ignite UI for Angular también admite la migración automática de versiones mediante los schematics `ng update`. Estos intentarán migrar todos los cambios importantes posibles (selectores, clases y propiedades @Input/@Output renombrados); sin embargo, puede que sigan existiendo cambios que no se puedan migrar. Normalmente están relacionados con la lógica TypeScript de la aplicación y se describen [más abajo](#cambios-manuales-adicionales).

Ejecute primero el comando [**`ng update`**](https://angular.io/cli/update), que analizará su aplicación y las actualizaciones disponibles de sus paquetes.

```cmd
ng update
```

Para actualizar el paquete con licencia de **Ignite UI for Angular**, ejecute el siguiente comando:

```cmd
ng update @infragistics/igniteui-angular
```

Para actualizar el paquete gratuito de **Ignite UI for Angular**, ejecute el siguiente comando:

```cmd
ng update igniteui-angular
```

Cuando actualice `@infragistics/igniteui-angular` o `igniteui-angular`, se recomienda actualizar también los paquetes `@angular/core`, `@angular/cli` y `igniteui-cli` a sus versiones correspondientes.
Para actualizar el paquete **Ignite UI CLI**, ejecute el siguiente comando:

```cmd
ng update igniteui-cli
```

Para actualizar el paquete **Angular Core**, ejecute el siguiente comando:

```cmd
ng update @angular/core
```

Para actualizar el paquete **Angular CLI**, use el siguiente comando:

```cmd
ng update @angular/cli
```

<DocsAside type="info">
Si el comando `ng update` falla por incompatibilidades de dependencias de paquetes, revierta la actualización, elimine la carpeta `node_modules` y vuelva a ejecutar la actualización con el indicador `--force`.
</DocsAside>

## Cambios manuales adicionales

Por desgracia, no todos los cambios pueden actualizarse automáticamente. Los cambios siguientes se dividen en secciones según aparecen en las versiones, así que, si necesita alguna actualización, empiece por su versión actual y aplique las siguientes de abajo hacia arriba.

Por ejemplo: si está actualizando de la versión 6.2.4 a la 7.1.0, empiece por la sección "From 6.x ..", aplique esos cambios y continúe hacia arriba:

## De 22.2.x a 22.3.x

Ignite UI for Angular 22.3.0 usa Ignite UI Theming 30 (`igniteui-theming`), cuya función `palette()` genera paletas con un nuevo generador `fitted` de forma predeterminada. El generador `fitted` coloca cada tono según el contraste y lo emite como un color fijo, por lo que una llamada a `palette()` se compila con colores distintos a los de antes. Las paletas predefinidas, como `$light-material-palette`, y los temas CSS prediseñados siguen usando el generador `legacy` y no cambian. [Generación de paletas](../themes/palette-generation.mdx) explica ambos generadores.

La migración `ng update` añade `$generator: 'legacy'` a cada llamada a la función `palette()` de sus archivos `.scss` y `.sass` que todavía no elija un generador, para que sus paletas conserven sus colores:

```scss
// Before
$my-palette: palette(
  $primary: #0099ff,
  $secondary: #df1b74,
  $surface: #ffffff
);

// After
$my-palette: palette(
  $primary: #0099ff,
  $secondary: #df1b74,
  $surface: #ffffff,
  $generator: 'legacy'
);
```

La migración deja sin cambios `@include palette(...)`, el mixin que emite una paleta como variables CSS. No puede añadir el argumento a una llamada que pase sus argumentos con spread, como `palette($args...)`. Al final de la salida de `ng update` informa de cada una de esas llamadas, con su archivo y su línea, así que añada usted mismo `generator: 'legacy'` al mapa del spread.

Para pasar una paleta al generador `fitted`, elimine el argumento `$generator`. Para mantener el generador `legacy` en todas las llamadas a `palette()` sin pasar el argumento, configure la biblioteca de temas antes de que cualquier otra cosa la cargue:

```scss
@use "igniteui-theming" with ($shade-generator: 'legacy');
@use "igniteui-angular/theming" as *;
```

Los temas de componente toman ahora su fondo del rol de superficie `base`, `--ig-surface-base`, en lugar de `--ig-surface-500`. Cada paleta emite los roles de superficie: `base`, `sunken`, `raised`, `overlay` y `container`. Los tonos de superficie numerados están obsoletos: las paletas los siguen emitiendo con ambos generadores, y una paleta `fitted` apunta `--ig-surface-500` a `--ig-surface-base`, pero se eliminarán en una versión futura. Revise lo siguiente manualmente:

- Si sobrescribe `--ig-surface-500` en tiempo de ejecución, por ejemplo para cambiar una sección a una superficie oscura, sobrescriba en su lugar `--ig-surface-base`, junto con `--ig-surface-raised`, `--ig-surface-overlay` y `--ig-surface-sunken` donde los use. Consulte [Paletas](../themes/palettes.mdx#dark-vs-light).
- Si sus propios estilos leen `--ig-surface-500` o `color($color: 'surface', $variant: 500)`, seguirán funcionando por ahora. Muévalos a un rol de superficie, como `color($color: 'surface')`, que devuelve `base`, antes de que se eliminen los tonos numerados.
- Si pasa un mapa de paleta escrito a mano, añada los roles de superficie a su entrada `surface`. Consulte [Mapas de paleta personalizados](../themes/sass/palettes.mdx#mapas-de-paleta-personalizados).

## De 22.0.x a 22.1.x

Ignite UI for Angular 22.1.0 termina la migración al mixin `tokens()` y traslada los estilos estructurales de cada componente a su propio bundle. La migración `ng update` realiza automáticamente los siguientes cambios sintácticos:

- Sustituye los mixins contenedores de Sass por componente que se han eliminado (`avatar`, `badge`, `banner`, `card`, `dialog`, `tabs`, los mixins de cuadrícula y de pivot, y el resto de contenedores que estaban obsoletos) por `tokens()`.
- Elimina las llamadas a los mixins `-typography` por componente eliminados, como `badge-typography`, `dialog-typography` y `checkbox-typography`. La tipografía se aplica ahora mediante tokens de componente. Consulte [Tipografía](/themes/sass/typography#tipografía-de-componentes) para las sobrescrituras específicas de cada componente.
- Elimina las importaciones profundas de Sass de parciales estructurales, como `igniteui-angular/lib/core/styles/components/avatar/avatar-component`, y sus llamadas `component()` correspondientes. Los estilos estructurales se incluyen ahora automáticamente en el bundle del componente.
- Renombra las importaciones directas y los usos de `IgxDividerDirective` a `IgxDividerComponent`. `IgxDividerModule` no se ve afectado.

Revise manualmente las llamadas `tokens()` migradas. La migración no puede determinar si un mixin contenedor representaba una sobrescritura de token universal ordinaria o si dependía de declaraciones locales de componente. Mantenga el modo global generado por defecto, salvo que las pruebas o la estructura del tema demuestren que se necesitan declaraciones locales. En ese caso concreto, añada `$mode: 'scoped'`:

```scss
// Before
.my-avatar {
  @include avatar(avatar-theme($background: red));
}

// After
.my-avatar {
  @include tokens(
    avatar-theme($background: red),
    $mode: 'scoped'
  );
}
```

Empiece con el modo global predeterminado, incluso al sustituir la mayoría de las llamadas a `css-vars()`. Si el componente sigue en la salida global de `theme()`, sus declaraciones locales pueden consumir los tokens universales y normalmente no se necesita ningún modo con ámbito.

Use el modo con ámbito solo cuando la salida predeterminada no proporcione las declaraciones locales del componente que necesita la personalización. Los casos típicos son:

- El contenedor eliminado establecía un tema local completo cuyo comportamiento no se conserva solo con las sobrescrituras de tokens universales.
- El componente aparece en la lista `$exclude` del mixin global `theme()`. En ese caso, el tema global no emite las declaraciones locales que consume la hoja de estilos estructural del componente.
- El tema usa expresiones de tamaño locales al componente. El modo global omite intencionadamente los valores de tamaño que dependen de variables de tamaño locales.
- El mapa del tema contiene varios selectores, como el host del componente y un selector de ghost u overlay. Las superposiciones separadas deben tematizarse desde un selector que pueda coincidir con la superposición en su outlet, normalmente en una hoja de estilos global.
- El tema local cambia el sistema de diseño o la variante clara/oscura. Pase la `$schema` correspondiente a la función de tema del componente para que el modo con ámbito emita los metadatos de tema correctos.

No añada el modo con ámbito de forma indiscriminada. Mantenga el modo global predeterminado para las sobrescrituras ordinarias de `--ig-<component>-*`, ya sean de toda la aplicación o restringidas por un selector. El componente debe seguir incluido en la salida global de `theme()`, para que sus declaraciones locales puedan consumir esos tokens universales:

```scss
@include tokens(
  avatar-theme(
    $schema: $dark-material-schema,
    $background: var(--ig-primary-500)
  )
);
```

El modo con ámbito no elimina universalmente la necesidad de `::ng-deep`. El encapsulado de vista emulado de Angular puede seguir impidiendo que los selectores generados para elementos anidados o internos coincidan. Conserve `::ng-deep` cuando las pruebas demuestren que es necesario, o traslade esa inclusión del tema a una hoja de estilos global. En el caso de una superposición separada, `::ng-deep` por sí solo no basta: el tema debe coincidir o heredarse en el outlet de la superposición.

Los estilos de Ignite UI usan ahora el orden de cascada `ig.reset` → `ig.base` → la capa del sistema de diseño activo (`ig.material`, `ig.bootstrap`, `ig.fluent` o `ig.indigo`) → `ig.derived`. Si su aplicación carga una hoja de estilos de reset o normalize, colóquela en la capa de reset de menor precedencia para que no pueda sobrescribir los estilos de los componentes:

```scss
@layer ig.reset {
  @import "minireset.css";
}
```

Para más detalles, consulte [Temas de componentes](/themes/sass/component-themes) y [Temas globales](/themes/sass/global-themes#excluir-componentes).

## De 21.1.x a 22.0.x

Angular ya no incluye `HammerModule` para los gestos táctiles. Para mantener las interacciones táctiles (arrastre, deslizamiento, toque) en los componentes de Ignite UI for Angular, cargue HammerJS como script global mediante el array `scripts` de su `angular.json`:

```json
"architect": {
  "build": {
    "options": {
      "scripts": [
        "node_modules/hammerjs/hammer.min.js"
      ]
    }
  }
}
```

Una vez cargado globalmente, Ignite UI for Angular detecta automáticamente `window.Hammer` y lo usa para gestionar los gestos táctiles; no se necesitan importaciones ni registros de módulos adicionales.

## De 21.0.x a 21.1.x

La versión 21.1.0 incluye un nuevo mixin `tokens` que puede usarse en lugar del mixin `css-vars`, ya obsoleto, de nuestro framework de temas de Sass. En apariencia es un cambio cosmético; sin embargo, el nuevo mixin `tokens` genera tokens de tema de componente globales universales que funcionan en todos nuestros frameworks de Ignite UI. El mixin `css-vars` está ahora obsoleto y se eliminará en una versión futura, así que le recomendamos cambiar al nuevo mixin `tokens` cuanto antes.

El mixin `tokens` genera tokens de variables CSS para los componentes en los modos `global` o `scoped`, con una cadena de reserva universal `--ig-*` y la reescritura correcta de las referencias a tokens locales.

**Modo global** (predeterminado): emite tokens universales `--ig-{component}-{property}`. Las referencias locales `var()` se reescriben a sus equivalentes globales para que los valores derivados (por ejemplo, `adaptive-contrast`) se resuelvan correctamente en cualquier ámbito. Las expresiones de tamaño se omiten; pase valores concretos en su lugar.

```scss
// Input:
@include tokens(avatar-theme($background: red));

// Output:
:root {
  --ig-avatar-background: red;
  /* ... remaining avatar properties ... */
}
```

**Modo con ámbito**: emite variables con ámbito de componente (`--{property}`) con una cadena de reserva: prefijo configurado (`--igx-*`) -> universal (`--ig-*`) -> valor predeterminado del esquema. Cuando se llama desde la raíz de la hoja de estilos, se usa la `selector` del tema para crear la regla. Cuando se llama dentro de un selector, tanto el selector actual como el selector del componente reciben las variables. En esencia, produce el mismo resultado que el mixin `css-vars`, ya obsoleto.

```scss
// Input (from root):
@include tokens(avatar-theme($background: red), $mode: 'scoped');

// Output:
igx-avatar {
  --background: var(--igx-avatar-background, var(--ig-avatar-background, red));
  /* ... remaining avatar properties ... */
}
```

```scss
// Input (from within a selector):
.my-theme {
  @include tokens(avatar-theme($background: red), $mode: 'scoped');
}

// Output:
.my-theme,
.my-theme igx-avatar {
  --background: var(--igx-avatar-background, var(--ig-avatar-background, red));
  /* ... */
}
```

<DocsAside type="info">
En el modo con ámbito, la propiedad `selector` del mapa de tema generado es necesaria para determinar el selector del componente y acotar correctamente las variables. Si el mixin se llama desde la raíz de la hoja de estilos, la regla generada usará el valor interno `selector` del tema. Si se llama desde dentro de un selector, tanto ese selector como el del componente recibirán las variables.
</DocsAside>

```scss
// Global override:
:root {
  @include tokens(avatar-theme($background: orange));
}
// Result: --ig-avatar-background: orange;

// Scoped consumption (no explicit override):
@include tokens(avatar-theme($schema: $schema), $mode: 'scoped');
// Result: --background resolves through var(--igx-avatar-background, var(--ig-avatar-background, #000))
//         and picks up the global orange value from --ig-avatar-background.
```

<DocsAside type="info">
**Las sobrescrituras globales fluyen hacia el modo con ámbito.** Como las variables con ámbito recurren a los tokens `--ig-*`, al establecer un token global en `:root` se propagará a todas las instancias con ámbito:
</DocsAside>

## De 20.x a 21.0.x

### Compatibilidad con múltiples puntos de entrada

La versión 21.0.0 introduce **múltiples puntos de entrada** para un mejor tree-shaking y división de código. El punto de entrada principal (`igniteui-angular`) sigue siendo totalmente compatible con versiones anteriores, pero se recomienda migrar a los puntos de entrada granulares para obtener tamaños de bundle óptimos.

**Cambios principales:**
- Componentes organizados en puntos de entrada dedicados (por ejemplo, `igniteui-angular/grids/grid`, `igniteui-angular/button`)
- Algunos componentes se han trasladado (directivas de entrada, autocompletado, grupo de radio)
- Cambio de nombre de tipo: `Direction` → `CarouselAnimationDirection`

**Migración:**

Al actualizar, se le pedirá que migre las importaciones automáticamente:

```cmd
ng update igniteui-angular
```

Elija **"Yes"** cuando se le pida, o migre más tarde con:

```cmd
ng update igniteui-angular --migrate-only --from=20.1.0 --to=21.0.0
```

Para ver todos los detalles sobre los puntos de entrada, las opciones de migración, los cambios importantes y los ejemplos de uso, consulte la [guía de división de código y múltiples puntos de entrada](/general/code-splitting-and-multiple-entry-points).

### Refactorización de la inyección de dependencias

Toda la inyección de dependencias interna usa ahora la API `inject()`. Esto normalmente no afecta al código de la aplicación, pero si extiende componentes o servicios de Ignite UI, es posible que tenga que actualizar sus constructores para usar `inject()` en lugar de parámetros del constructor.

## De 17.0.x a 17.1.x

### General

- `IgxGrid`, `IgxTreeGrid`, `IgxHierarchicalGrid`
  - **Cambios importantes**
    - Los eventos `rowAdd` y `rowDelete` emiten ahora un argumento de evento de tipo `IRowDataCancelableEventArgs` en lugar de `IGridEditEventArgs`. Las dos interfaces siguen siendo compatibles, pero las propiedades `cellID`, `newValue`, `oldValue`, `isAddRow` son redundantes en estos eventos y están obsoletas en `IRowDataCancelableEventArgs`, y se eliminarán en una versión futura. Al cambiar a las interfaces nuevas correctas, deberían aparecer los usos obsoletos que pueden eliminarse sin riesgo.
  - **Obsolescencias**
    - La propiedad `rowID` está obsoleta en las siguientes interfaces: `IGridEditDoneEventArgs`, `IPathSegment`, `IRowToggleEventArgs`, `IPinRowEventArgs`, `IgxAddRowParent` y se eliminará en una versión futura. Use `rowKey` en su lugar.
    - La propiedad `primaryKey` está obsoleta en las siguientes interfaces: `IRowDataEventArgs`, `IGridEditDoneEventArgs`. Use `rowKey` en su lugar.
    - La propiedad `data` está obsoleta en la siguiente interfaz: `IRowDataEventArgs`. Use `rowData` en su lugar.

### Cambios importantes

- En la versión 17.1.x, el tipo `icon` de la directiva `igxButton` se ha cambiado por la directiva `igxIconButton` de tipo `flat`. Hay migraciones automáticas disponibles y se aplicarán en `ng update`. Sin embargo, algunas de las propiedades de entrada de `igxButton` que antes podían usarse con botones de tipo `icon` no pueden aplicarse a los `igxIconButton` recién creados. Si ha usado las propiedades `igxButtonColor` o `igxButtonBackground` con un botón de tipo `icon`, debe actualizarlo de la siguiente manera:

```html
// version 17.0.x
<button igxButton="icon" [igxButtonBackground]="'red'">
    <igx-icon fontSet="material">search</igx-icon>
</button>

// version 17.1.x
<button igxIconButton="flat" [style.background]="'red'">
    <igx-icon fontSet="material">search</igx-icon>
</button>
```

**NOTA**: los usuarios deben añadir manualmente `IgxIconButtonDirective` a sus importaciones:

```typescript
import { IgxIconButtonDirective } from 'igniteui-angular';

@Component({
    ...
    imports: [IgxIconButtonDirective]
})
```

## De 16.1.x a 17.0.x

### General

- En la versión 17.0, Angular ha eliminado los paquetes `@nguniversal/*`. Si el proyecto usa estos paquetes, una llamada estándar a `ng update` provocará un error en las migraciones de `igniteui-angular` debido a `package-lock.json` modificados incorrectamente; más detalles en [el issue #13668](https://github.com/IgniteUI/igniteui-angular/issues/13668). Para actualizar a `17.0.x`, hay que seguir uno de los pasos adicionales siguientes:
  - Elimine el archivo `package-lock.json` antes de ejecutar `ng update`
  - Ejecute `npm dedupe --legacy-peer-deps` antes de ejecutar `ng update igniteui-angular`

**Cambio importante**

- En los argumentos del evento `selectionChanging` de `IgxCombo`, el tipo `IComboSelectionChangingEventArgs` tiene estos cambios:
  - Las propiedades `newSelection` y `oldSelection` se han renombrado a `newValue` y `oldValue`, respectivamente, para reflejar mejor su función. Al igual que `value` de Combo, emitirán los valores de propiedad especificados o los elementos de datos completos según se haya establecido `valueKey` o no. Hay migraciones automáticas disponibles y se aplicarán en `ng update`.
  - Se exponen dos propiedades nuevas, `newSelection` y `oldSelection`, en lugar de las anteriores, que ya no se ven afectadas por `valueKey` y emiten de forma coherente los elementos de `data` de Combo.
  - Las propiedades `added` y `removed` contienen ahora siempre elementos de datos, con independencia de si `valueKey` está establecido. Así se alinean con las propiedades `newSelection` y `oldSelection` actualizadas.

Si su código del manejador del evento `selectionChanging` dependía de leer `valueKeys` desde el argumento del evento, actualícelo de la siguiente manera:

```typescript
  // version 16.1.x
  public handleSelectionChanging(e: IComboSelectionChangingEventArgs): void {
    this.addedItems = e.added;
    this.removedItems = e.removed;
  }

  // version 17.0.x
  public handleSelectionChanging(e: IComboSelectionChangingEventArgs): void {
    this.addedItems = e.added.map(i => {
       return i[e.owner?.valueKey]
    });
    this.removedItems = e.removed.map(i => {
       return i[e.owner?.valueKey]
    });
  }
```

- `getCurrentResourceStrings` se ha eliminado. Use en su lugar las importaciones de cadenas de componente específicas.
  - Por ejemplo, las cadenas en EN proceden de `igniteui-angular`: `import { GridResourceStringsEN } from 'igniteui-angular';`
  - Por ejemplo, las cadenas en DE u otros idiomas proceden de `igniteui-angular-i18n`: `import { GridResourceStringsDE } from 'igniteui-angular-i18n';`

    Puede encontrar ejemplos de uso en la documentación actualizada de [Localización (i18n)](/general/localization).

## De 16.0.x a 16.1.x

### General

#### **Cambios no importantes**

- Nos alejamos del token de inyección `DisplayDensityToken` como forma de establecer el tamaño de los componentes, en favor de una forma más sencilla y robusta: las propiedades personalizadas de CSS. Por ese motivo, el token de inyección `DisplayDensityToken` está ahora obsoleto. Esto afecta a todos los componentes que exponen la propiedad de entrada `displayDensity`. El token y las propiedades de entrada se eliminarán en la versión 17.0.0. Le recomendamos hacer lo siguiente:

Elimine todas las declaraciones en las que se proporciona `DisplayDensityToken`:

```typescript
// *.component.ts
// remove the provider declaration for `DisplayDensityToken`
providers: [{ provide: DisplayDensityToken, useValue: { displayDensity: DisplayDensity.compact } }],
```

Elimine todos los enlaces o asignaciones programáticas a la propiedad de entrada `displayDensity`:

```html
{/* Remove `[displayDensity]="'compact'"` */}
<igx-grid [displayDensity]="'compact'">...</igx-grid>
```

En su lugar, use la propiedad personalizada de CSS `--ig-size` para obtener el mismo resultado que con `displayDensity`:

```css
/* 
Add --ig-size to a component or global file.
Available values are:
  - compact: --ig-size-small
  - cosy: --ig-size-medium
  - comfortable: --ig-size-large
*/
igx-grid {
    --ig-size: var(--ig-size-small);
}
```

## De 15.1.x a 16.0.x

- La actualización a Angular 16 incluye cambios en el funcionamiento interno de `NgModules`. Antes, añadir un módulo que dependía internamente de otro hacía que las declaraciones de ambos estuvieran disponibles en su aplicación. Ese comportamiento no era intencionado y Angular 16 lo cambia. Si su aplicación dependía de este comportamiento (por ejemplo, si solo importaba un módulo que contiene muchas dependencias internas, como `IgxGridModule`, y usaba componentes que vienen con ellas), tendrá que añadir manualmente los módulos de cada componente que use su aplicación por separado.

- **Cambios importantes**
- En la versión 16.0.x se eliminan todas las propiedades de la cuadrícula relacionadas con la paginación. El comportamiento de la paginación se configura y controla ahora íntegramente mediante `IgxPaginatorComponent`.
Para activar la paginación en la cuadrícula, inicialice `IgxPaginatorComponent` en la cuadrícula, establezca las propiedades de entrada relacionadas y adjunte los manejadores de eventos al propio paginador:

```html
<igx-grid ...>
    <igx-paginator #paginator [totalRecords]="totalRecords" [perPage]="25" (pageChange)="pageChange($event)" (perPageChange)="perPageChange($event)">
    </igx-paginator>
</igx-grid>
```

```typescript
@ViewChild('grid', { static: true }) private grid: IgxGridComponent;
@ViewChild('paginator', { static: true }) private paginator: IgxPaginatorComponent;

// prior version 16.0.x
public onButtonClick(event) {
    this.grid.nextPage();
    this.grid.previousPage();
    this.grid.paginate(0);
}

// from version 16.0.x
public onButtonClick(event) {
    this.paginator.nextPage();
    this.paginator.previousPage();
    this.paginator.paginate(0);
}
```

- En la versión 16.0.x se elimina el método de cuadrícula `getCellByColumnVisibleIndex(rowIndex: number, index: number)`. En su lugar, use: `getCellByKey(rowSelector: any, columnField: string)` o `getCellByColumn(rowIndex: number, columnField: string)`. Ejemplo:

```typescript
 // prior version 16.0.x
 const cell = grid.getCellByColumnVisibleIndex(rowIndex, columnIndex);

 // after version 16.0.x
 const rowKey = grid.getRowByIndex(rowIndex).key;
 const columnField = grid.getColumnByVisibleIndex(columnIndex).field;
 const cell = grid.getCellByKey(rowKey, columnField);
 const cell = grid.getCellByColumn(rowIndex, columnField);
```

## De 15.0.x a 15.1.x

- **Cambio importante**
- Ha cambiado el tipo de los argumentos de `rowSelectionChanging`. Ahora las colecciones `oldSelection`, `newSelection`, `added` y `removed`, que forman parte de la interfaz `IRowSelectionEventArgs`, ya no contienen las claves de fila de los elementos seleccionados (cuando la cuadrícula tiene establecido un primaryKey), sino que en todos los casos se emiten los datos de la fila. Cuando la cuadrícula trabaja con datos remotos y se establece un `primaryKey`, para las filas seleccionadas que no forman parte actualmente de la vista de la cuadrícula se emitirá un objeto de datos de fila parcial.

Si su código del manejador del evento `rowSelectionChanging` dependía de leer primaryKeys desde el argumento del evento, actualícelo de la siguiente manera:

```typescript
  // prior version 15.1.x
  public handleRowSelection(e: IRowSelectionEventArgs): void {
    this.selectedRows = e.newSelection;
  }

  // after version 15.1.x
  public handleRowSelection(e: IRowSelectionEventArgs): void {
    this.selectedRows = e.newSelection.map(rec => {
       return rec[e.owner?.primaryKey]
    });
  }
```

    ```scss
            @include avatar($avatar);
        }
    ```

- Módulos de Sass:
El motor de temas ha pasado a usar [módulos de Sass](https://sass-lang.com/documentation/at-rules/use). Este cambio significa que todas las funciones de la biblioteca de temas (temas de componente, etc.), los mixins (mixins de componente, etc.) y las variables se `forwarded` ahora desde un único archivo. Para usar correctamente la biblioteca de temas de Sass, su proyecto debe usar Dart Sass versión 1.33.0 o posterior, y cambiar todas las importaciones de la biblioteca de temas de:

```scss
// free version
@import '~igniteui-angular/lib/core/styles/themes/index';

// licensed version
@import '~@infragistics/igniteui-angular/lib/core/styles/themes/index';
```

a:

```scss
// free version
@use 'igniteui-angular/theming' as *;

// licensed version:
@use '@infragistics/igniteui-angular/theming' as *;
```

Si quiere importar toda la biblioteca de temas una sola vez y usarla después en otros archivos de Sass de la aplicación, asegúrese de reexportarla. Los archivos de Sass importados no se reexportan automáticamente.

Antes:

```scss
// _variables.scss
// free version
@import '~igniteui-angular/lib/core/styles/themes/index';

// licensed version
@import '~@infragistics/igniteui-angular/lib/core/styles/themes/index';

// _other-file.scss
@import 'variables';
```

Después:

```scss
// _variables.scss
// free versioin
@use 'igniteui-angular/theming' as *;
@forward 'igniteui-angular/theming';

// licensed version
@use '@infragistics/igniteui-angular/theming' as *;
@forward '@infragistics/igniteui-angular/theming';

// _other-file.scss
@use 'variables' as *;
```

- Paletas y esquemas:

- Las variables CSS de paleta ya no hacen referencia a valores HEX; ahora representan una lista de 3 valores H, S y L, lo que significa que deben pasarse a las funciones CSS `hsl` o `hsla`.

Antes:

```scss
.some-class {
    background: var(--igx-surface-500); // returns HEX color
}
```

Después:

```scss
.some-class {
    background: hsl(var(--igx-surface-500)); // returns a list of H, S, L
}
```

Esto se hizo para que las paletas puedan cambiarse en tiempo de ejecución usando solo variables CSS. Así, el canal alfa de un color de paleta concreto puede modificarse en tiempo de ejecución sin afectar al color de la paleta subyacente.

- Asegúrese de pasar la paleta y el esquema de componente correctos a sus temas globales y de componente personalizados. Si quiere crear un tema oscuro global, asegúrese de elegir un tono de gris más claro, por ejemplo:

```scss
$my-dark-palette: palette(
    $primary: olive,
    $secondary: yellow,
    $grays: #fff
);

@include dark-theme($palette: $my-dark-palette);
```

Del mismo modo, los temas claros requieren un tono de gris más oscuro y un esquema de color claro.

Si no ha excluido ningún tema de componente del tema global, pero aun así quiere crear sus propios temas de sustitución usando el mixin `css-vars`, asegúrese de que al tema se le pase la paleta correcta y el esquema correspondiente:

```scss
$my-custom-grid: grid-theme(
    $palette: $my-dark-palette,
    $schema: $dark-schema
);

@include css-vars($my-custom-grid);
```

- Temas de componente excluidos:

Si ha excluido algunos temas de componente del tema global y ha creado temas de sustitución personalizados, asegúrese de que se incluye el mixin del componente y de que se le pasa el tema de componente correcto:

```scss
$my-dark-palette: palette(
    ...
    $exclude: ('igx-grid')
);

$my-custom-grid: grid-theme(
    $palette: $my-dark-palette,
    $schema: $dark-schema
);

// Ensuregrid is included:
@include grid($my-custom-grid);
```

Si sus temas de componente personalizados se declaran en un archivo Sass de componente independiente, distinto del `styles.scss` global, asegúrese de que también se incluya el mixin `core`.

```scss
// free version
@use 'igniteui-angular/theming' as *;

// licensed version
@use '@infragistics/igniteui-angular/theming' as *;

// Include the core module mixin.
@include core();

// Create your theme.
$my-custom-grid: grid-theme(
    $palette: $my-dark-palette,
    $schema: $dark-schema
);

// Include your custom theme styles.
@include grid($my-custom-grid);
```

Para comprender mejor el sistema de módulos de Sass, puede leer [este excelente artículo](https://css-tricks.com/introducing-sass-modules/) de [Miriam Suzanne](https://css-tricks.com/author/miriam/);

### Temas

Debido a las quejas relacionadas con las advertencias de compilación (véase [#9793](https://github.com/IgniteUI/igniteui-angular/issues/9793)), ahora usamos la función [`math.div`](https://sass-lang.com/documentation/modules/math#div); esta funcionalidad es compatible con [Dart Sass](https://sass-lang.com/dart-sass) desde la versión 1.33.0 en adelante.

#### Solución

Si por algún motivo ve errores de compilación de Sass que indican que `math.div` no es una función conocida, significa que está usando una versión obsoleta de Sass en su proyecto.

1. Actualice a la última versión de Angular usando `ng update`: Angular 12.1.0 o posterior usa el compilador dart-sass de forma predeterminada.

    ```sh
    ng update [options]
    ```

    Si por algún motivo no usa Ignite UI/Angular CLI, tendrá que reemplazar `node-sass` por `sass` en su proyecto de Node.

    ```sh
    npm uninstall node-sass
    npm install sass --save-dev
    ```

2. Si por algún motivo no puede actualizar a la última versión de Angular con el método anterior, puede volver al método antiguo de división de Sass estableciendo un indicador global en su archivo Sass:

    ```scss
    $__legacy-libsass: true;
    ```

    ```typescript
    }
    ```

  - Como `animateOnRelease` y `dropFinished()` también están quedando obsoletos, cualquier uso del método `dropFinished()` debe sustituirse por `transitionToOrigin()`. De lo contrario, tendría que llamar a `transitionToOrigin()` según el momento en que quiera que el elemento arrastrado vuelva a su ubicación original. Tenga en cuenta que, si cambia la posición en el DOM del elemento arrastrado, su ubicación original también cambiará en consecuencia.

- IgxDrop
  - Como la estrategia de colocación predeterminada que proporciona la directiva `IxgDrop` ya no se aplica por defecto, para seguir teniendo el mismo comportamiento debe establecer la nueva entrada `dropStrategy` en la implementación `IgxAppendDropStrategy` proporcionada.

    ```html
    <div igxDrop [dropStrategy]="appendStrategy"></div>
    ```

    ```typescript
    import { IgxAppendDropStrategy } from 'igniteui-angular';
    // import { IgxAppendDropStrategy } from '@infragistics/igniteui-angular'; for licensed package

    public appendStrategy = IgxAppendDropStrategy;
    ```

  - Cualquier uso de las interfaces `IgxDropEnterEventArgs` y `IgxDropLeaveEventArgs` debe sustituirse por `IDragBaseEventArgs`.
  - Además, cualquier uso de la interfaz `IgxDropEventArgs` debe sustituirse por `IDropDroppedEventArgs`.

- IgxRowDragDirective
  - `IRowDragStartEventArgs` y `IRowDragEndEventArgs` tienen ahora los nombres de sus argumentos cambiados para que quede más claro a qué se refieren. El argumento `owner` se renombra a `dragDirective`.
    El argumento `owner` proporciona ahora una referencia al componente propietario. Si su código era así:

    ```typescript
    public dragStart(event) {
        const directive = event.owner;
    }
    ```

    A partir de la versión 8.2.x debe actualizarse a:

    ```typescript
    public dragStart(event) {
        const directive = event.dragDirective;
        const grid = event.owner;
    }
    ```

- IgxCombo
  - Ha cambiado la forma en que [`igx-combo`](/inputs/combo/overview) gestiona la selección y el enlace de datos.

  - Si se define la entrada [`valueKey`] del combo, el control buscará esa propiedad concreta en el array de elementos de datos pasado al realizar la selección.
**Todos** los eventos de selección se gestionan con el valor de la propiedad `valueKey` de los elementos de datos.
    Todos los combos que tengan especificado `valueKey` deben tener su selección o enlace bidireccional formado solo por los valores de la propiedad del objeto indicada en la entrada:

    ```html
    <igx-combo [data]="cities" valueKey="id" displayKey="name"></igx-combo>
    ```

    ```typescript
    export class MyExampleCombo {
        public data: { name: string, id: string }[] = [{ name: 'London', id: 'UK01' }, { name: 'Sofia', id: 'BG01' }, ...];
        ...
        selectFavorites() {
            // Selection is handled with the data entries' id properties
            this.combo.selectItems(['UK01', 'BG01']);
        }
    }
    ```

  - Si el combo **no** tiene definido `valueKey`, **todos** los eventos de selección se gestionan mediante **igualdad (===)**.
    Todos los combos que **no** tienen especificado `valueKey` deben gestionar su selección o enlace bidireccional mediante **referencias** a sus elementos de datos:

    ```html
    <igx-combo [data]="cities" displayKey="name"></igx-combo>
    ```

    ```typescript
    export class MyExampleCombo {
        public data: { name: string, id: string }[] = [{ name: 'London', id: 'UK01' }, { name: 'Sofia', id: 'BG01' }, ...];
        ...
        selectFavorites() {
            // Selection is handled with references to the data entries
            this.combo.selectItems([this.data[0], this.data[1]]);
        }
    }
    ```

    Puede leer más sobre cómo configurar el combo en el [readme](https://github.com/IgniteUI/igniteui-angular/blob/master/projects/igniteui-angular/src/lib/combo/README.md#value-binding) y en la [documentación oficial](/inputs/combo/overview#value-and-selection).

```css
.pagination-container {

}
```

## De 7.0.x a 7.1.x

- Si usa un IgxGrid con resúmenes en su aplicación, debe saber que ahora el método `IgxSummaryOperand.operate()` se llama con datos vacíos para calcular la altura necesaria de la fila de resumen. En el caso de operandos de resumen personalizados, el método debe devolver siempre un array de IgxSummaryResult con la longitud adecuada.

 Antes de la versión 7.1:

```typescript
export class CustomSummary extends IgxNumberSummaryOperand {
 public operate(data?: any[]): IgxSummaryResult[] {
  return [{
   key: 'average',
   label: 'average',
   summaryResult: IgxNumberSummaryOperand.average(data).toFixed(2)
  }];
 }
}
```

 Desde la versión 7.1:

```typescript
export class CustomSummary extends IgxNumberSummaryOperand {
 public operate(data?: any[]): IgxSummaryResult[] {
  return [{
   key: 'average',
   label: 'average',
   summaryResult: data.length ?  IgxNumberSummaryOperand.average(data).toFixed(2) : null
  }];
 }
}
```
